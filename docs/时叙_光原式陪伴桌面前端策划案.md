# 时叙 × 「光原式」陪伴桌面 —— 前端内嵌策划案（初稿）

> 来源：抖音视频（作者 Lumi_mao，关键词「光原」），104 秒竖屏实拍。
> 本文档：分析视频中的前端形态，评估把时叙 Agent 内嵌进这种样式的可行性、优缺点与技术需求。
> 日期：2026-08-12

---

## 一、视频里是什么

一款 **AI 陪伴桌面产品**（配套毛绒硬件「毛先生」，发光蓝眼睛，放在显示器旁）。软件界面是一个深色氛围的「陪伴桌面」，布局四分区：

| 区域 | 内容 | 作用 |
|---|---|---|
| 左侧 | 应用坞（彩色圆角图标，类 AI OS launcher） | 旁白提到「您有自己的 Agent 团队」——每个图标是一个 Agent / 功能入口 |
| 中央 | **语音粒子球**（金橙色粒子聚成球体，红色氛围光底） | 数字生命的视觉主体，随说话律动——产品的「灵魂焦点」 |
| 右侧 | 状态仪表盘（柱状图、数值卡、滑块） | 陪伴数据可视化：记忆/状态/系统信息 |
| 底部 | 控制条（麦克风 + 功能按钮 + 提示文字） | 语音交互入口 |

旁白是一段真实陪伴对话：「你觉得你现在有够了解我吗」「但这只是 46 天的碎片拼出来的画像」「毛先生这 46 天没白过」——卖点是**长期陪伴 + 记忆累积 + 有「存在感」的视觉主体**。

### 交互范式对比

| | 传统聊天界面（时叙现状） | 视频形态（陪伴桌面） |
|---|---|---|
| 主体 | 消息列表 | 粒子球（视觉生命体） |
| 文字 | 主角 | 配角（字幕/浮层） |
| 导航 | 侧边栏 | 应用坞（Agent 团队） |
| 氛围 | 工具感 | 陪伴感、沉浸感 |
| 数据 | 记忆管理页 | 常驻仪表盘 |

## 二、与时叙的映射：已有什么，缺什么

### 已有（直接复用，这是时叙的优势）

- **灵魂完整**：persona + 4 面具 + 情绪识别 + reply_mode，视频的「说话直接」式对话时叙已经能做到
- **记忆体系**：锚点 / 行为观察 / 待跟进 / 主动开启话题——「46 天碎片拼出画像」正是时叙记忆域的设计目标
- **语音闭环**：ASR（Faster-Whisper）→ `/ws/chat` → 浏览器 TTS → 插话打断，且 done 事件带 `reply_mode / emotion_state`——粒子球的情绪驱动数据源现成
- **前端底座**：Vue3 + Pinia + Naive UI；已有 `VrmAvatar.vue`（three.js/VRM）和 `DeviceSimulator.vue` 等组件，WebGL 管线已通

### 缺（需要新建）

1. **粒子球视觉体**（核心）：three.js 粒子系统 + 音频律动 + 情绪着色
2. **沉浸式布局**：从「聊天窗 + 侧栏」改为「球为中心、聊天退为字幕浮层」的陪伴模式
3. **状态仪表盘**：记忆统计 / 面具分布 / 情绪曲线可视化（后端数据已有，需加聚合 API）
4. **应用坞导航**：把记忆管理、文件产出、研究工具等包装成「Agent 团队」图标入口（偏包装，工作量小）
5. （可选）**桌面化外壳**：Electron 打包，贴近视频的「桌面常驻」形态
6. （远期）**硬件联动**：视频里的毛绒宠物属硬件范畴，软件侧预留接口即可

## 三、可行性分析

**结论：可行，且时叙是这类产品里「灵魂先行」的少见案例——视觉层是纯前端工程，风险低。**

| 维度 | 评估 |
|---|---|
| 技术难度 | 中。粒子球是成熟方案（three.js Points + 噪声场 + 音频振幅驱动），无算法壁垒 |
| 数据依赖 | 无新增。情绪/面具/语音振幅全部来自现有 WS 事件流和 Web Audio API |
| 后端改动 | 极小。仅仪表盘需要 1~2 个聚合统计 API（只读，不动对话链路） |
| 风险 | 主要风险是「观感调优」——粒子球好不好看 90% 在参数调教，不在代码 |
| 与现有路线兼容性 | 高。可作为「陪伴模式」开关与现有聊天模式并存，不破坏 V1 链路，测试不受影响 |

**关键判断：数字人 VRM 路线当时卡在模型观感；粒子球路线绕开了「拟人脸」的恐怖谷，抽象粒子反而没有观感门槛，且和「时叙是被养出来的」叙事更契合（球随记忆数据生长/变化）。**

## 四、优缺点

### 优点
1. **陪伴感质变**：从「和一个文本框说话」变成「和一个有存在感的生命体相处」，与产品定位完全一致
2. **差异化**：粒子球 + 记忆生长可视化的组合，避开与 VRM 数字人竞品的正面比拼
3. **前端自给自足**：复用现有 WS 协议、语音闭环、事件流；后端几乎零侵入
4. **可分阶段交付**：粒子球单独就是完整可用的 P0，不存在半成品状态
5. **测试友好**：视觉层与对话逻辑解耦，现有 178+31 个测试不受影响

### 缺点
1. **调参成本高**：粒子运动的「生命感」靠大量细节参数（噪声频率、呼吸幅度、颜色过渡），需要反复肉眼调校
2. **性能开销**：数万粒子 + 60fps 渲染，低端设备需降级方案（粒子数减半 / 静态fallback）
3. **信息密度下降**：聊天退为字幕后，长文本阅读、文件产物展示体验变差——所以必须保留「聊天模式」切换，而非取代
4. **移动端适配另算**：视频形态是桌面横屏，手机竖屏需要单独布局设计

## 五、需要的技术

### 核心（P0 粒子球）
| 技术 | 用途 | 备注 |
|---|---|---|
| three.js（已随 VRM 引入） | 粒子系统渲染 | `THREE.Points` + 自定义 ShaderMaterial |
| GLSL shader | 粒子形变/噪声场/发光 | simplex noise 顶点扰动，fresnel 边缘光 |
| Web Audio API `AnalyserNode` | 语音律动 | TTS 播放流 + 麦克风采集流双源驱动（`audio/` 模块已有采集） |
| 现有 WS done 事件 | 情绪着色 | `emotion_state / reply_mode / mask` → 粒子颜色与运动节奏 |

### 布局与面板（P1）
| 技术 | 用途 |
|---|---|
| Vue3 组件 + CSS | 沉浸式全屏布局、字幕浮层、模式切换 |
| ECharts | 右侧仪表盘（记忆增长曲线、面具分布、情绪时间线） |
| 后端聚合 API（FastAPI 只读端点） | `/api/stats/*` 统计锚点数、消息数、面具使用分布 |

### 可选（P2/P3）
| 技术 | 用途 |
|---|---|
| Electron / Tauri | 桌面常驻外壳（推荐 Tauri，包体积小） |
| Web Serial / WebSocket | 远期硬件宠物联动（预留） |
| prefers-reduced-motion 适配 + 粒子数分级 | 性能降级与无障碍 |

## 六、分期建议

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0** | 陪伴模式：粒子球 + 字幕浮层 + 语音律动 + 情绪着色 | 语音对话时球随声音律动；emo/comfort 等状态颜色可区分；可与聊天模式互切 |
| **P1** | 仪表盘 + 统计 API + 应用坞（包装现有功能入口） | 右侧面板展示真实记忆数据；应用坞可打开记忆管理/文件列表 |
| **P2** | 桌面外壳（Tauri）+ 性能分级 + 开机自启 | 双击即用，无需手动起服务 |
| **P3** | 硬件联动预研（串口协议/现成 plush 方案） | 仅出预研结论 |

**建议先做 P0 的一个「静帧原型」：不动交互，先把球画出来调观感——观感过关再铺交互，避免走数字人那次「做完又拆」的回头路。**

---

## 七、风险与注意

1. **不要动对话链路**：陪伴模式只是 `ChatView` 的另一种渲染，WS 协议、面具路由、记忆副作用零改动
2. **保留聊天模式**：文件产物、长文阅读仍需要列表形态，两种模式并存是底线
3. **粒子球的「养成感」可以绑定记忆数据**（如锚点数量 → 球的大小/亮度/粒子密度）——这是时叙独有的差异化，视频产品没有这一点，值得写进设计
