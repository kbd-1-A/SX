# 时叙：数字人陪伴 Agent 后续开发方案

版本：V1.0  
日期：2026-08-07  
目标目录：E:\时序-txt  

## 1. 产品判断

时叙现在已经不是一个空项目，它已经具备“文字陪伴 Agent”的骨架：可以聊天、有核心人格、有面具、有会话历史、有初步记忆、有流式输出，也已经做过 VRM 数字人的技术验证。

但如果目标是“数字人里面封装我的 Agent 功能 + 语音 + 表情功能”，那它还需要从“会聊天的文本 Agent”升级为“有关系感、有记忆、有主动性、有多模态表达的陪伴型 Agent”。

我的产品判断是：

- 当前工程骨架完成度：约 60%
- 相对完整数字人陪伴 Agent 的完成度：约 30% - 35%
- 下一阶段重点不应该先追求复杂 UI，而应该补齐记忆、主动跟进、语音链路和数字人表达四个核心闭环

## 2. 陪伴型 Agent 应具备的核心能力

一个真正有陪伴感的 Agent，不只是“能回答问题”，而是要在长期互动里让用户感到它认识我、记得我、会接住我、会在合适的时候回来找我。

### 2.1 稳定人格

需要具备：

- 清晰的人设、语气、价值观和边界
- 稳定的称呼、关系感和表达习惯
- 不同场景下的模式切换，比如朋友、助手、倾听者、执行者
- 不因为单轮提示词变化而人格漂移

时叙现状：

- 已有核心人格 `shisu.md`
- 已有 4 个面具和 `reply_mode`
- 已有轻量语气保护
- 还缺人格评测、边界约束、长期一致性检查

### 2.2 长期记忆

需要具备：

- 记住用户事实：昵称、偏好、重要关系、重要事件
- 记住情绪和状态：最近压力、目标、困扰、期待
- 记住承诺和待办：下次要问什么、什么时候跟进
- 允许用户查看、编辑、删除、禁止记忆
- 能处理记忆冲突、过期和隐私边界

时叙现状：

- 已有结构化记忆锚点
- 已有昵称、关系里程碑等雏形
- 还缺记忆确认、记忆管理页面、冲突处理、过期机制、主动检索策略

### 2.3 情绪理解与回应策略

需要具备：

- 识别用户当下状态：开心、低落、焦虑、疲惫、愤怒、敷衍
- 根据状态决定回应方式：安慰、陪伴、转移、追问、行动建议
- 能区分“用户想被听见”和“用户想解决问题”
- 避免机械安慰和过度说教

时叙现状：

- 已有基础语气控制和人设表达
- 还缺显式情绪状态、对话策略评分、敏感场景处理

### 2.4 主动陪伴

需要具备：

- 记住用户说过的事情，并在合适时间主动跟进
- 能形成开放事项，比如“明天面试”“月底考试”“今天说要早睡”
- 能发起复盘、提醒、问候、鼓励
- 主动行为必须可控，用户能关掉或调整频率

时叙现状：

- 当前主要是被动对话
- 缺少时间引擎、提醒系统、开放事项列表、主动消息策略

### 2.5 多模态表达

需要具备：

- 语音输入：用户可以说话
- 语音输出：Agent 可以用声音回应
- 打断能力：用户能中断正在说的话
- 数字人表情：微笑、关切、专注、惊讶、思考
- 口型同步：说话时嘴部跟随语音变化
- 身体小动作：眨眼、点头、呼吸感、视线跟随

时叙现状：

- 已有 VRM 渲染组件验证
- 当前 UI 已移除 VRM，原因是模型观感问题
- 还缺 ASR、TTS、口型同步、表情状态机、动作编排

### 2.6 安全、隐私与用户控制

需要具备：

- 隐私透明：告诉用户记住了什么
- 用户可删除：一键删除记忆和会话
- 风险场景处理：自伤、极端情绪、违法请求、医疗法律金融建议
- 陪伴边界：不能诱导依赖，不能假装具备真实人类身份

时叙现状：

- 已有基础工程能力
- 还缺完整安全策略、用户隐私面板、敏感内容分级和评测

## 4. 后续要开发的内容

### 4.1 第一优先级：把文字 Agent 做稳

目标：让时叙先成为一个稳定、可信、能长期聊的陪伴 Agent。

要做：

- 梳理核心人格和面具边界
- 建立 30 - 50 条固定测试对话，用来检查语气、记忆、边界
- 优化上下文拼接策略，避免回复越来越散
- 增加异常处理：模型超时、WebSocket 断开、回复中断、空回复
- 建立基础日志，记录每轮请求、耗时、失败原因

### 4.2 第二优先级：补齐记忆系统

目标：让用户感觉“它真的记得我”，同时能控制自己的数据。

要做：

- 记忆候选提取：从对话中提取可能值得记住的内容
- 记忆确认：重要记忆先询问用户是否保存
- 记忆分类：偏好、事实、关系、事件、目标、禁忌
- 记忆编辑页：查看、修改、删除、关闭记忆
- 记忆冲突处理：新旧信息矛盾时询问用户
- 记忆过期：临时状态不要永久影响人格判断
- 记忆检索：根据当前对话自动召回相关记忆

### 4.3 第三优先级：主动陪伴与时间引擎

目标：让时叙从“你问我答”变成“会惦记事”的陪伴对象。

要做：

- 开放事项列表：记录需要后续关心的事情
- 主动跟进策略：根据时间、重要程度、用户状态决定是否提醒
- 用户可控频率：安静、正常、积极三档
- 每日问候和晚间复盘
- 重要事件前后提醒，比如考试、面试、约会、项目截止
- 前端展示“待跟进事项”和“最近关心点”

### 4.4 第四优先级：语音输入与语音输出

目标：让对话从打字升级为自然说话。

要做：

- 前端录音：Web Audio / MediaRecorder
- ASR 服务：先做 provider 抽象，不锁死某个供应商
- TTS 服务：支持云端 TTS 或本地 TTS
- 回复打断：用户说话或点击停止时，中断当前文本和音频
- 音频状态：聆听中、思考中、说话中、已暂停
- 音色配置：后续支持不同音色和语速

建议实现顺序：

- 第一版先做“按住说话”
- 第二版做“点击开始/停止”
- 第三版再考虑实时双工语音和 WebRTC

### 4.5 第五优先级：数字人、表情和口型

目标：让 Agent 的人格通过可见形象表达出来，而不是只靠文本。

要做：

- 替换当前占位 VRM，制作更符合时叙气质的模型
- 保留模型加载失败兜底 UI
- 自动眨眼和轻微呼吸动画
- 表情状态机：平静、微笑、关切、专注、惊讶、思考
- 情绪映射：根据 Agent 回复内容和对话状态选择表情
- 口型同步：第一版用音量驱动，后续升级到 viseme
- 视线和头部动作：看向用户、轻点头、思考时偏头
- 前端状态统一：文本流、音频播放、表情、口型共享同一个 Agent 状态

### 4.6 第六优先级：安全、隐私和部署

目标：让产品能被真实使用，而不只是本地 Demo。

要做：

- 记忆隐私面板
- 导出和删除用户数据
- 敏感内容识别与兜底回复
- API Key 管理和服务端安全
- 前后端打包
- 基础测试和运行文档
- Windows 本地启动脚本
- 后续多用户版本再迁移数据库

## 5. 开发周期

按单人全职开发估算，建议 12 周完成一个可体验的 V1 数字人陪伴 Agent。  
如果是业余学习型开发，更合理的周期是 16 - 20 周。

| 周期 | 阶段 | 目标 | 交付物 |
| --- | --- | --- | --- |
| 第 1 周 | 稳定文字 Agent | 修复基础体验，建立评测样本 | 稳定聊天、测试对话集、基础日志 |
| 第 2 - 3 周 | 记忆系统 | 让记忆可确认、可查看、可删除 | 记忆提取、记忆管理页、检索策略 |
| 第 4 - 5 周 | 主动陪伴 | 让 Agent 能跟进用户事件 | 开放事项、提醒、主动问候 |
| 第 6 - 7 周 | 语音链路 | 支持说话输入和语音回复 | ASR、TTS、打断、音频状态 |
| 第 8 - 10 周 | 数字人表达 | 接入 VRM、表情、口型、动作 | 数字人页面、表情状态机、口型同步 |
| 第 11 周 | 安全隐私 | 用户能控制记忆和风险边界 | 隐私面板、安全策略、兜底话术 |
| 第 12 周 | 打磨交付 | 可稳定演示和本地部署 | 启动脚本、验收清单、演示版本 |

### 6.1 前端

| 主框架 | Vue 3 + Vite + TypeScript | 保留当前项目技术栈 |
| 状态管理 | Pinia | 管理会话、Agent 状态、音频状态、数字人状态 |
| UI 组件 | Naive UI | 保留现有风格，后续可逐步建立自己的设计系统 |
| 3D 渲染 | Three.js | VRM 数字人渲染 |

| 音频输入 | Web Audio / MediaRecorder | 录音、音量分析、打断检测 |
| 语音合成 | speechSynthesis / 云端 TTS | 原型可用浏览器 TTS，正式版接 provider |
| 图标 | Lucide | 页面控制按钮、导航图标 |

### 6.2 后端

| 类型 | 技术 | 说明 |
| --- | --- | --- |
| API 服务 | FastAPI | 保留现有后端 |
| 实时通信 | WebSocket | 支持流式文本、状态推送、停止回复 |
| 数据库 | SQLite | 当前阶段足够，单机学习和 Demo 成本低 |
| 未来数据库 | PostgreSQL | 多用户、权限、生产部署时再迁移 |
| 记忆检索 | SQLite FTS / 标签检索 | 先做轻量检索，后续再加向量库 |
| 向量检索 | sqlite-vec / pgvector | 后续做语义记忆召回 |
| 定时任务 | APScheduler | 本地版主动提醒和跟进 |
| 生产队列 | Redis + RQ/Celery | 多用户和复杂任务后再引入 |
| 模型接口 | OpenAI-compatible API | 保持 DeepSeek、OpenAI、本地模型可替换 |

### 6.3 语音与数字人 Provider 设计

不要在第一版锁死供应商。建议抽象三个接口：

- `LLMProvider`：负责文本生成
- `ASRProvider`：负责语音转文字
- `TTSProvider`：负责文字转语音

这样后续可以在 DeepSeek、OpenAI、本地模型、Whisper、本地 faster-whisper、云端 TTS 之间切换，不需要重写产品逻辑。

## 7. 技术难点

### 7.1 记忆不是简单保存聊天记录

真正难点是判断“什么值得记住、什么时候使用、什么时候忘掉”。如果所有内容都记住，Agent 会变得啰嗦、冒犯甚至不准确。

解决方向：

- 只保存高价值信息
- 重要记忆先征求用户确认
- 给记忆设置类型、置信度、更新时间和过期时间
- 回复前只召回少量相关记忆

### 7.2 主动陪伴容易打扰用户

主动不是越多越好。陪伴型 Agent 的主动性必须有分寸，否则会变成干扰。

解决方向：

- 用户可设置主动频率
- 重要事件优先，闲聊问候降权
- 明确区分提醒、关心、复盘、建议
- 所有主动事项都可关闭

### 7.3 语音体验的延迟和打断

语音一旦延迟太高，体验会明显变差。TTS 说话时如果不能打断，也会显得笨重。

解决方向：

- 第一版采用按住说话，降低实时性压力
- 文本流和音频流分离
- 前端维护统一状态：聆听中、思考中、说话中、暂停
- 支持用户点击或再次说话时立即停止回复

### 7.4 数字人表情要和对话状态同步

数字人如果只是在屏幕上站着，不会带来陪伴感。真正关键是“它的表情和正在说的话一致”。

解决方向：

- 给 Agent 回复附带情绪标签
- 前端根据情绪标签切换 VRM 表情
- 说话时启动口型，停止时恢复平静
- 眨眼、呼吸、视线移动作为常驻轻动画

### 7.5 VRM 模型资产质量

当前占位模型能验证技术，但不一定符合时叙的产品气质。数字人产品的形象会强烈影响用户第一感受。

解决方向：

- 先用占位模型完成交互链路
- 后续单独设计时叙形象
- 统一服装、发型、色彩、表情风格
- 模型大小要控制，避免加载慢

### 7.6 安全和边界

陪伴型 Agent 不能只追求“像真人”，还必须让用户知道它是 AI，并且在高风险场景里有边界。

解决方向：

- 明确 AI 身份
- 敏感话题进入安全策略
- 危机情绪提供现实支持建议
- 记忆和会话可删除

## 8. 你可以学习到什么

做完这个项目，你能学到的不只是“调 API”，而是一整套 AI 产品从原型到可体验版本的能力。

你会学到：

- 如何设计陪伴型 Agent 的产品结构
- 如何写稳定人格和多面具提示词
- 如何做流式对话和 WebSocket 状态同步
- 如何设计长期记忆系统
- 如何做主动提醒和时间事件
- 如何接入 ASR 和 TTS
- 如何用 Three.js 加载 VRM 数字人
- 如何控制数字人的表情、眨眼、口型和动作
- 如何做前后端工程拆分
- 如何设计用户隐私、记忆权限和安全边界
- 如何从 Demo 走向可演示、可迭代的真实产品

这条学习路线很适合你，因为它同时覆盖产品经理、前端、后端、AI Agent、语音交互和数字人表达。它不是单点技术，而是一个完整 AI 应用系统。

## 11. 验收标准

V1.0 前建议用以下标准判断是否合格：

- 用户能连续聊天 10 分钟以上，不出现明显人格崩坏
- Agent 能记住用户确认过的重要事实
- 用户可以查看、修改、删除记忆
- Agent 能基于过去事件进行合适跟进
- 支持语音输入和语音输出
- 用户可以随时打断回复
- 数字人能正常加载
- 数字人有眨眼、表情和说话口型
- 移动端和桌面端布局不重叠、不溢出
- 遇到敏感场景有基本安全兜底
- 本地启动流程清晰，普通用户能按文档运行

## 12. 下一步执行建议

我建议从两个方向并行推进：

- 工程侧：先做记忆管理和主动跟进，因为这是陪伴感的底层
- 表现侧：先用占位 VRM 打通表情、口型、语音，不急着追求最终形象

最合理的下一个开发任务是：

1. 给现有后端增加“记忆确认、编辑、删除”接口
2. 给前端增加“记忆管理抽屉”
3. 给聊天回复增加“情绪标签”和“动作标签”
4. 在 VRM 页面里根据动作标签驱动表情
5. 接入浏览器 TTS 验证说话和口型同步

做到这一步，时叙就会从“能聊天”明显升级到“有陪伴感”。
