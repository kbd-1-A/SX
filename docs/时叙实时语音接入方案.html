时叙 · 实时全双工语音接入方案

目标：在时叙实现 GPT-Live 式全双工实时语音（边听边说 / 随时打断 / 区分停顿与说完） · 基于 DashScope（阿里百炼）· 2026-08-26
一句话结论：时叙现在的 Faster-Whisper ASR → qwen-flash LLM → 浏览器 SpeechSynthesis TTS 是半双工回合制管道，做不到"同时听说"。要复刻 GPT-Live，必须改用服务端 VAD + 流式 ASR + 流式 TTS + 语音打断的 duplex 链路。阿里 DashScope 提供现成能力，且有一套能复用时叙现有 LLM 管道（人格 / 记忆 / 面具 / 工具）的方案——不必从零重造时叙的核心资产。

一、背景与现状

GPT-Live（2026 年 7 月上线）两个核心特征：①全双工实时对话——边听边说、随时打断、AI 区分"停顿思考"和"说完"；②自然无指令门槛——无需唤醒词，像真人聊天。

时叙现状（陪伴模式语音闭环）：

环节现用问题
听（ASR）Faster-Whisper 本地需要 VAD 切段，说完才转写
想（LLM）qwen-flash（DashScope OpenAI 兼容）非流式生成，整句才出
说（TTS）浏览器 SpeechSynthesis整句合成，不可打断回退
打断有插话打断（VAD 检测用户说话时停 TTS）但她生成时你没法说，她说时你没法插——本质半双工回合制

二、核心概念：为什么拼接管道做不到全双工

全双工的实质：你说的时候她在听、同时在生成；她说的时候她仍在听你（你随时能插话打断）。这要求音频持续双向流 + 服务端实时 VAD + 流式响应。

时叙现在的链路是单向分时：你说话→VAD 判定说完→ASR 转写→LLM 生成（此时你只能等）→TTS 合成（此时你只能听）。哪怕加再多 VAD 和打断优化，也只是"快速切换说话权"，不是"同时听说"。要真正复刻 GPT-Live，链路必须从回合制改成持续双工流。

三、阿里的两套方案（关键权衡）

查官方文档发现，DashScope 有两套都能做全双工的方案，对时叙意义完全不同：

路径 A 推荐 — multimodal-dialog duplex（拼接式全双工）

  • 地址：wss://dashscope.aliyuncs.com/api-ws/v1/inference，模型 multimodal-dialog
  • 本质：流式 ASR + 你指定的 LLM + 流式 TTS，duplex 模式 = 持续上传音频 + 服务端 VAD + 语音打断（你随时说话就能打断她输出）
  • ASR 可选：Paraformer / qwen3-asr-flash-realtime 等
  • TTS 可选：CosyVoice-v2/v3/v3.5 / qwen3-tts 等（支持声音复刻）
  • 关键：LLM 环节是可配置的——时叙能复用现有 qwen-flash + 人格 shisu.md + 4 面具路由 + 记忆 + 工具，这些核心资产一个不丢
  • 延迟：LLM 单环节约 3.1s（官方实测），比端到端快约 2s
  • 消息流：Start → Started → DialogStateChanged(Listening) → 持续上传音频 → 服务端 VAD → RespondingStarted → 流式文本/音频 → RespondingEnded → LocalRespondingEnded

路径 B 可选 — Qwen-Omni-Realtime（端到端全双工）

  • 地址：wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=qwen3.5-omni-plus-realtime
  • 本质：端到端语音模型（音频进→音频出，一条模型内完成 ASR+理解+TTS）
  • 支持 WebRTC（浏览器 UDP 直连，内置回声消除降噪）/ WebSocket / AOQ
  • 智能更强：语义打断（避免"嗯哼"附和声误触发打断）、语音控制语速音量情绪、原生联网搜索、Function Calling
  • 音色：55 种官方 + 声音复刻（plus/flash 支持）
  • 代价：绕过时叙 LLM 管道——人格只能塞进 session.instructions（system prompt），记忆上下文受限（plus 100 轮 / 600s 音频），4 面具路由 / 工具 / 主动陪伴这些时叙特性挂不上或要重做
  • 延迟：约 5.1s（flash）~5.8s（plus），比拼接慢约 2s
维度路径 A 拼接 duplex路径 B 端到端 Omni
复用时叙人格/记忆/面具/工具能，LLM 环节可配难，绕过 LLM 管道
响应延迟约 3.1s（LLM 环节）约 5.1~5.8s
打断智能度语音打断（说话即停）语义打断（更准，不误触）
音色CosyVoice，支持复刻55 种 + 复刻
联网搜索/工具需自己在 LLM 环节接原生支持（二者不可同开）
改造量中（换 ASR/TTS 链路 + 加桥接）大（实时模式独立，人格/记忆重接）

四、推荐：路径 A（拼接式 duplex）

推荐路径 A 的理由：时叙花了大力气建的人格分层、记忆画像、4 面具路由、工具（文件/研究/音乐/天气）、自主学习反馈——这些都是绑在 LLM 管道上的核心资产。路径 A 的 LLM 环节可配，意味着实时语音模式能原样复用这套管道，只把"听"和"说"换成流式 + 服务端 VAD + 语音打断。改造集中在 I/O 两端，不动大脑。路径 B 更智能但等于在时叙里另起一个独立对话脑，人格/记忆/面具要重新设计接入，得不偿失。

路径 B 可作为后续 P2 探索：当时叙的实时语音跑顺后，若想要"语义打断 / 语音控制情绪"这类更强能力，再评估是否引入 Omni 作为"高智能实时模式"（与路径 A 共存，用户可选）。

五、架构设计

当前（半双工）

# 回合制
浏览器(麦克风流) → 本地VAD切段 → Faster-Whisper ASR → qwen-flash → SpeechSynthesis → 播放
     ↑                                                                          ↓
     └──────────────────── 插话打断(检测到说话则停TTS) ←──────────────────────────┘

改造后（全双工 duplex）

# 持续双工流，LLM 环节复用时叙现有管道
浏览器(麦克风流, 每100ms)
   │  二进制PCM 16k mono
   ↓
后端 WS 桥接 (FastAPI) ──duplex──▶ DashScope multimodal-dialog
   │                                   │
   │                                   ├─ 服务端 VAD (自动检测说完)
   │                                   ├─ 流式 ASR (Paraformer/qwen3-asr)
   │                                   ├─ LLM = 时叙 qwen-flash + shisu人格 + 面具路由 + 记忆 + 工具
   │                                   └─ 流式 TTS (CosyVoice, 可复刻音色)
   │                                   ↓
   │                              RespondingStarted / 流式文本 / 流式音频 / RespondingEnded
   │  ← SSE/WS 回推 ←──────────────┘
   ↓
浏览器播放(流式音频) + 字幕流  +  语音打断(你说话服务端VAD检测到即停她输出)

新增组件

  • 前端：陪伴模式加"实时语音"开关；开启后 getUserMedia 拿麦克风流，ScriptProcessor/AudioWorklet 每 100ms 取 PCM 16k mono，二进制帧发后端 WS；同时 WS/SSE 接收流式音频回放 + 字幕流
  • 后端：新增 backend/realtime/bridge.py，FastAPI WS 端点 /ws/voice，作为浏览器 ↔ DashScope 的 duplex 桥接：上行把浏览器 PCM 透传给 DashScope，下行把 DashScope 的流式文本/音频推回浏览器
  • 鉴权：API Key 留后端 .env，不下发浏览器（官方明确：客户端持有 Key 有安全风险）

六、关键技术点

1. duplex 模式启动

# Start 消息（后端发给 DashScope）
{
  "header": {"action":"run-task","task_id":"","streaming":"duplex"},
  "payload": {
    "task_group":"aigc","task":"multimodal-generation","function":"generation",
    "model":"multimodal-dialog",
    "input":{"directive":"Start","workspace_id":"WS_ID","app_id":"APP_ID"},
    "parameters":{
      "upstream":{"type":"AudioOnly","mode":"duplex","audio_format":"pcm","sample_rate":16000},
      "downstream":{"voice":"longxiaochun_v2","sample_rate":24000,"intermediate_text":"transcript,dialog"},
      "client_info":{"user_id":"shisu_user"},
      "biz_params":{"user_defined_params":{"extra_config":{"enable_web_search":false}}}
    }
  }
}

关键：mode:"duplex" 开启双工；streaming:"duplex" header 字段固定；intermediate_text:"transcript,dialog" 同时拿用户识别结果和 AI 回答中间结果（字幕用）。

2. 时序约束（容易踩的坑）

官方明确：收到 Started 不能立即发音频。必须等 DialogStateChanged 事件且 state==Listening 才能开始推音频。提前发会丢数据。这是 duplex 模式的第一道同步闸。

3. 持续音频上传

# 100ms 一帧，16k 16bit mono
# 每帧字节数 = 16000 * (16/8) * 100/1000 = 3200 bytes
ws.send_binary(pcm_3200_bytes)  # 每100ms

duplex 模式下持续上传，任何状态超 20s 不上传即报错。浏览器 AudioWorklet 每 100ms 产出 3200 字节 PCM 透传后端。

4. 服务端 VAD + 语音打断（全双工的核心）

  • 服务端自动检测语音起止：检测到说完 → 触发 LLM 响应
  • 语音打断：duplex 模式下你随时说话，服务端 VAD 检测到 → 立即停止当前 AI 输出，转入听你
  • 客户端无需手动管理打断——这是 duplex 区别于 tap2talk 的关键（tap2talk 只能发 RequestToSpeak 消息打断，不能语音打断）

5. 流式响应接收

# DashScope 下行事件（后端转推浏览器）
RespondingStarted           # AI 开始响应
RespondingContent(transcript) # 中间文本（字幕增量）
二进制音频帧                 # 流式 PCM 24k，直接播
RespondingEnded             # AI 响应结束
# 浏览器播完后回：
LocalRespondingEnded        # 通知服务端播放结束（duplex 下推进状态机）

6. 心跳保活

官方规定任意连续 60s 服务端没向客户端发消息就断连。静默时后端要定期发 HeartBeat，服务端回应保活。

7. 单会话上限

Omni 120 分钟；multimodal-dialog 需查限流。长陪伴要设计会话续接（带 dialog_id 续接历史）或定时重建并落库记忆。

七、人格 / 记忆 / 面具 / 工具如何挂

路径 A 的最大价值：LLM 环节可配，时叙现有管道原样复用。
  • 人格：multimodal-dialog 的 LLM 环节接时叙 agents/persona.py，shisu.md 灵魂照常作为 system 前缀注入
  • 4 面具：实时语音里也能跑 agents/mask.py 路由——ASR 转出的用户文本进面具选择，选中的面具层注入 LLM
  • 记忆：流式 ASR 的最终转写进 memory/ 画像系统，和文本模式共享同一个记忆库
  • 工具：LLM 环节若走时叙自己的 qwen-flash 调用（而非 multimodal-dialog 内置 LLM），文件/研究/音乐/天气工具照常可用。需确认 multimodal-dialog 是否允许 LLM 环节外挂时叙自有推理，否则LLM 环节有两种接法：
    1. 用 multimodal-dialog 内置 LLM（人格靠 prompt 注入，工具能力受限）
    2. ASR/TTS 用 DashScope，LLM 仍走时叙自有 qwen-flash + 工具管道——把 DashScope 只当"流式 ASR + 流式 TTS + VAD"用，LLM 环节时叙自己拼。这需要确认 multimodal-dialog 是否支持"只取 ASR/TTS、LLM 外接"的模式
待验证点（P0 前要先问清）：multimodal-dialog 的 LLM 环节是固定内置还是允许外接时叙自有 qwen-flash 调用。若允许，路径 A 完美复用时叙全部资产；若固定内置，则人格靠 prompt、工具受限于 multimodal-dialog 的 Function Calling/MCP 能力。这点决定 P0 的接法，建议开工前先开个工单或在控制台试一个最小 Start 消息确认。

八、文本模式 ↔ 实时语音模式切换

  • 陪伴模式左上角控制台（已做的齿轮面板）加"实时语音"开关
  • 关闭时：维持现状（WS /ws/chat + 半双工 ASR/TTS）
  • 开启时：切到 WS /ws/voice duplex 桥接，停用本地 Faster-Whisper 和浏览器 SpeechSynthesis，音频走 DashScope 流式
  • 两模式共享：人格、记忆、面具、工具、字幕浮层、粒子球。切换时 WS 连接互换，对话上下文从记忆库续
  • 夜静音 / 自动朗读 / 语速音调等控制台设置在实时模式下映射到 downstream 参数（voice/speech_rate/pitch_rate）

九、实施阶段

P0 · 最小可用全双工（1-2 天）

  1. 后端 backend/realtime/bridge.py + FastAPI /ws/voice，实现 Start → Started → 等 DialogStateChanged(Listening) → 透传音频双向上行下行
  2. 前端陪伴模式加开关 + AudioWorklet 取 PCM 16k → WS；流式音频 AudioContext 播放 + 字幕流
  3. 先用 multimodal-dialog 默认 LLM 跑通"能说能听能打断"
  4. 验证：你说她在听，你随时能打断她，字幕流正常

P1 · 接入时叙人格/记忆/面具/工具（3-5 天）

  1. 确认 multimodal-dialog LLM 环节外接可行性（见第七节待验证点）
  2. 若可外接：LLM 环节改走时叙 agents/persona.py + 面具路由 + 工具
  3. 若不可外接：人格靠 downstream.instruction / prompt 注入，工具受限，记录差距
  4. ASR 转写落 memory/，与文本模式共享记忆
  5. 会话续接（dialog_id）+ 长时记忆落库

P2 · 打磨与增强（按需）

  • 声音复刻（CosyVoice clone）——用你自己的音色（需录 10s 样本，控制台确认状态 OK）
  • 控制台设置映射 downstream 参数（语速/音调/音量/音色）
  • 心跳保活 + 断线重连
  • 语义打断探索：评估路径 B（Qwen-Omni-Realtime）作为"高智能实时模式"是否值得加为可选
  • 语音控制情绪/语速（Omni 原生支持，路径 A 需自己接指令解析）

十一、前置条件

  • DashScope API Key：已有（qwen-flash 配的那个），同平台复用
  • Workspace ID + App ID：multimodal-dialog 方案需要这两个（控制台"多模态交互开发套件"→业务空间详情/我的应用）。若用 Omni-Realtime 路径则只需 Workspace ID
  • 开通服务：百炼控制台开通 multimodal-dialog 或 Qwen-Omni-Realtime 模型权限
  • 地域：华北2（北京）或新加坡，时叙后端部署在靠近地域处降延迟
  • 后端：FastAPI 加 websockets 依赖，新增 /ws/voice 端点（不影响现有 /ws/chat）
  • 前端：浏览器 getUserMedia + AudioWorklet（现代浏览器原生支持，无新依赖）
"WebSocket 是全双工通信协议，双方可互相主动推送数据"——官方文档原话。duplex 模式下持续上传音频 + 服务端 VAD + 语音打断，就是 GPT-Live 式"边听边说随时打断"的工程实现。
