## 2. 轮次 1：`.md / .txt` 双扩展名支持

### 2.1 现象

用户要求「创建 txt 文件放到桌面」，时叙回复「第一版文件工具只支持创建 .md Markdown 文件」。
方案文档第 17 节承诺「仅创建 .md 和 .txt」，但代码只实现 `.md`。

### 2.2 根因

`backend/app/tools/files.py` 的扩展名校验只放行 `.md`（`validate_markdown_filename`），
意图正则只识别 `md/markdown`。`research.py` 的研究意图已识别 `txt`，卡点仅在文件工具。

### 2.3 修复内容

- `files.py`：新增 `_SUPPORTED_EXTENSIONS = {md, txt}`；意图正则 `_FILE_NOUN`、
  `_NAMED_TEXT_FILE` 支持 `.txt`；`validate_markdown_filename` 用 `Path.suffix` 放行
  `.md/.txt`；同名排重改用 `Path.stem/.suffix`；`.txt` 返回 `text/plain` mime。
- `action_guard.py`：能力边界文案改为「.md 或 .txt」，`_FILE_REQUEST` 正则加入 `txt`。
- `chat.py`：成功消息按扩展名显示（`.txt` → 「已创建 文本文件」），失败消息通用化。
- `frontend/src/stores/chat.ts`：`ChatArtifact.mime_type` 扩展为 `'text/markdown' | 'text/plain'`。
- 测试：`test_file_tool.py` 更新拒绝用例（`.txt`→`.pdf`），新增 3 个 `.txt` 用例。

### 2.4 验证

后端 208 passed（当时基线），前端 39 passed，生产构建通过；
真实桌面创建 `.txt`（`text/plain`、SHA-256 校验）成功。

## 3. 轮次 2：正文不展示 + 草稿被污染

### 3.1 现象

用户打开时叙创建的文档，内容只有「已创建 Markdown 文件：…位置：…SHA-256…」+ 来源列表，
**没有分析正文**。用户反馈「他给出检索范围 但是检索出来的内容没有给出了 用户不看检索范围 看内容」。

### 3.2 根因（数据库与文件系统交叉比对确认）

- 模型在 document_draft 模式下，受**历史消息里上一轮的「已创建 Markdown 文件：…SHA-256…」
  成功提示**影响，把编造的创建提示（含模型臆造的 3.4KB / SHA 值）当成「草稿」输出。
- 该草稿绕过校验直接落盘 → 文件内容 = 编造成功提示 + 来源附录。
- 行动请求时草稿 chunk 不发送给前端 → 用户聊天里只看到成功提示 + 研究来源卡片。
- 文件名推导失败时退化为无意义的「时叙文档」。

### 3.3 修复内容

- `router.py`：`build_messages` 在 `document_draft=True` 时，过滤历史中的
  「行动结果消息」（以「已创建/文档文件没有创建成功/已读取/联网检索未完成」开头），
  模型不再有模仿对象。
- `chat.py`：
  - `_draft_unusable()`：检测「已创建/位置：/SHA-256」污染草稿 → 降级为研究框架，不落盘污染内容。
  - `_format_body_preview()`：文件创建成功后，把正文（≤600 字符，超长截断）作为 chunk
    先展示给用户，再发成功提示。
  - `_derive_query_filename()`：文件名优先从研究主题生成（用户要 txt 则 `.txt`），
    不再依赖草稿 H1。
- 测试：`test_chat_ws.py` 新增「污染草稿降级」用例，更新 3 个现有用例。

### 3.4 验证

后端全量通过；真实 LLM 端到端（session 6 历史含成功提示）：文件名
`AI 销售行情_2026-08-25.txt`，内容为真实分析正文（`# AI 销售行情分析` 开头、
带 [S#] 引用、含「未独立核实」标注），污染检测 False。

## 4. 轮次 3：深度报告（「我需要的是这种分析」）

### 4.1 现象

时叙生成的文档只有一句「好的，我准备了一份关于 AI 销售行情的分析文档草稿，内容基于
你提供的公开资料整理。」+ 来源列表（716 字节），用户需要的是完整 8 章节深度分析报告。

### 4.2 根因

- 模型输出「元描述」（说自己准备了草稿）而非正文，`_draft_unusable` 只检测
  「已创建/SHA-256」类污染，抓不到「寒暄无正文」。
- document_draft 提示词未明确报告结构要求，模型自由度大。
- 研究来源上限 `RESEARCH_MAX_SOURCES=4`，素材偏少。

### 4.3 修复内容

- `router.py` `format_document_draft_rules()`：要求生成**完整研究报告**——按顺序包含
  核心结论 / 市场规模与增速 / 主要细分赛道 / 主要玩家 / 风险与挑战 / 未来趋势 /
  给读者的建议 7 个章节，600 字以上，每章把资料转化为分析并用 [S#] 引用，
  禁止「我准备了一份…草稿」等元描述。
- `chat.py`：
  - `_draft_unusable()` 增强：无 `#` 标题 / 长度 <120 / 含「我准备了一份」等元描述 → 不可用。
  - 新增 `_retry_draft()`：草稿不可用时**自动重新生成一次**，第二次仍不可用才降级研究框架。
- `config.py`：`RESEARCH_MAX_SOURCES` 4 → 6。
- 测试：`test_chat_ws.py` 新增「元描述草稿自动重试」用例和 `_draft_unusable` 单测。

### 4.4 验证

后端全量通过；真实 LLM 端到端：文件名 `AI 销售行情_2026-08-25.txt`，长度 **2535 字符**，
**7 个章节全部齐全**，带 [S1][S2][S3] 引用、待核实标注，无元描述。

## 5. 轮次 4：话题理解（「我问他新的东西 他还是给我导出的ai销售行情分析」）

### 5.1 现象

用户问「帮我分析一下 最近的ai模型，创建 txt 文件放到桌面」，时叙仍生成
「AI 销售行情分析（基于非实时知识整理）」并落盘。

### 5.2 根因（意图解析实测确认）

- `_RESEARCH_SIGNAL` 信号词只有「研究/调研/行情/行业/市场/最新/现在/当前/趋势」，
  **没有「分析」和「最近」** → `parse_research_request` 返回 None → 研究未触发 →
  走「基于非实时知识」模式。
- 无研究资料时，模型被历史里多次「AI 销售行情」对话带偏，沿用旧话题写作。

### 5.3 修复内容

- `research.py`：
  - `_RESEARCH_SIGNAL` 加入「分析/最近/近期/如何/怎么样/评估/盘点」。
  - `_QUERY_FILLER` / `_QUERY_STOPWORDS` 加入「最近/近期」等口语词。
  - 实测：`parse_research_request("帮我分析一下 最近的ai模型，创建 txt 文件放到桌面")`
    → query = **`ai模型`**。
- `router.py`：document_draft 基础规则新增「**严格按用户当前这条请求的主题写作；
  历史对话里的其他主题（如之前的行情报告）不得沿用或混入本文档**」。
- 测试：`test_research.py` 新增「分析最近X」解析用例（含变体）。

### 5.4 验证

后端全量通过；真实 LLM 端到端（session 6 历史全是销售行情）：文件名 `ai模型_2026-08-25.txt`，
内容 `# 2026 年 AI 模型选型快评`（DeepSeek-R1、开源大模型格局），**全文零「销售行情」字样**。

## 6. 轮次 5：天气查询功能（新增能力）

### 6.1 背景

用户提出「北京（昌平）实时天气」示例，希望时叙能回答实时天气，并询问是否需要接入 API。
结论：需要天气数据源（个人项目推荐和风天气 QWeather 免费版），时叙按现有 Provider 抽象接入。

### 6.2 实现内容

- **`backend/app/services/weather.py`（新建）**：
  - 和风天气免费版 API（`devapi.qweather.com`）：城市搜索 `geo/lookup`、实时天气 `weather/now`、3 日预报 `weather/3d`。
  - `extract_city_name()`：从消息提取城市名——优先「XX区/县」（剥离城市前缀，如"北京昌平区"→"昌平区"），再「XX市」，再常见城市词表（70+ 城市）。
  - 数据类 `WeatherResult` / `WeatherForecast`（含 `as_event()` / `as_text()` / `format_weather_context()`）。
  - 未配置 API Key 时抛出 `WeatherError("weather_disabled")`，绝不编造天气。
- **`config.py`**：`WEATHER_ENABLED`、`WEATHER_API_KEY`、`WEATHER_API_BASE`、`WEATHER_TIMEOUT_SECONDS`、`WEATHER_DEFAULT_CITY`。
- **`action_guard.py`**：`ActionKind` 增加 `"weather"`；识别"天气/下雨/气温/温度/多少度/冷不冷/热不热/天气预报"；能力边界文案与兜底同步更新。
- **`router.py`**：`build_messages` / `stream_reply` 增加 `weather_result` 参数，注入 `format_weather_context`（"只能依据以上数据回答，不得编造"）。
- **`chat.py`**：`action_kind == "weather"` 分支——提取城市（无城市且无默认城市则询问）→ `fetch_weather_summary` → 流式回复；API 失败如实说明"天气暂时查不到"。
- **`.env.example`**：新增 `WEATHER_API_KEY` / `WEATHER_DEFAULT_CITY` 说明。

### 6.3 防幻觉设计

- 天气回复只能基于服务端 API 真实返回的数据；无 Key / API 失败 / 城市找不到都如实说明，不编造温度、降水或预报。
- 天气数据作为「不可信数据包」注入模型（与研究资料同策略），prompt 明确"只能依据以上数据回答"。

### 6.4 环境问题（顺带修复）

- Python 3.13.14 + pydantic 2.13.4 存在**间歇性原生崩溃**（access violation，pydantic `_namespace_utils` / openai 导入字节码编译阶段）。
- 处理：**pydantic 降级 2.13.4 → 2.12.5**（pydantic-core 2.46.4 → 2.41.5）+ 清理损坏的 `__pycache__`；此后全量测试稳定通过。
- 测试排障中发现 `test_chat_ws.py` 天气测试曾因 `fake_stream` 内 `kwargs["document_draft"]` KeyError（天气分支不传该参数）导致挂起——已改为在测试主体断言。

### 6.5 验证

- 后端全量 **223 passed**（新增 `test_weather.py` 6 个单测 + `test_chat_ws.py` 3 个天气集成测试）。
- 生产实测（未配 Key）：对时叙说"上海今天下雨吗"→ 提取"上海"→ 如实回复"天气功能还没有配置 API Key，暂时查不了天气"。
- 配置 Key 后预期回复：*"上海 16:55 实况：大雨，28℃，体感 32℃；西北风 3 级，湿度 93%… 未来 3 日：雷阵雨转小雨 22~29℃"*。

## 10. 已知限制与后续建议

1. **话题纠错**：模型偶尔仍可能跑题（概率性），用户说「不是这个，我说的是 XXX」可纠正；
   若需更强约束，可考虑在服务端做「草稿主题关键词相关性校验」（比对用户请求与草稿主题词）。
2. **来源质量**：Bing/360 搜索对中文长尾主题可能返回二手来源偏多；可考虑接入官方
   报告源或增加来源等级加权。
3. **重试代价**：草稿不合格自动重试会多一次 LLM 调用（耗时/成本），当前仅研究型文档触发；
   若频率过高可加单轮最多重试次数限制（当前 1 次）。
4. **研究框架降级**：搜索失败时保存「研究框架」文档并如实说明，不会伪造实时结论——
   用户如需重试可直接再发一次请求。
5. **天气**：和风免费版有 QPS / 每日调用限制（个人项目够用）；城市提取目前依赖词表与
   后缀规则，生僻地名可能识别不到（可后续接行政区划数据）；`WEATHER_DEFAULT_CITY` 可作兜底。
6. **环境**：Python 3.13 下 pydantic 曾出现间歇性原生崩溃，已降级 2.12.5 规避；
   升级 pydantic 前建议先跑全量测试确认稳定。
